# Kronagent — AWS deployment & least-privilege wiring

This directory holds the AWS-side prerequisites for running Kronagent against a real
account. The design principle is **least privilege for the responder itself**:
Kronagent's own credentials must be able to perform *only* the specific containment
actions the executor makes, so a compromised or misbehaving agent has a bounded
blast radius. `kronagent-iam-policy.json` grants exactly those calls and nothing
else.

> The policy is **apply-ready** (valid IAM grammar, no annotations that AWS
> would reject). All the "why" lives here in the README.

## 0. Self-Serve 3-Click CloudFormation Onboarding

For multi-tenant or multi-account deployments, Kronagent supports zero-key cross-account onboarding via CloudFormation templates located in [`deploy/cloudformation/`](cloudformation/):

1. **`kronagent-observe-role.json`**: Deploys the **Read-Only (Observe)** IAM role for threat telemetry ingestion, findings triage, and resource inspection. Zero state-changing permissions.
2. **`kronagent-contain-role.json`**: Deploys the **Containment (Contain)** IAM role for active remediation (disabling access keys, swapping security groups, NACL blocking).

Both templates enforce the **STS External ID condition** (`sts:ExternalId`) unique per tenant to defend against the *confused deputy* attack. The customer launches the stack directly from pre-filled console links generated by `kronagent/connect.py`.


## 0b. Run Kronagent inside your own account (one stack)

[`cloudformation/kronagent-in-account.json`](cloudformation/kronagent-in-account.json)
runs Kronagent **in** the account it protects, instead of granting an outside
Kronagent a role into it. Findings, the audit log and the model calls stay in
the account.

```
GuardDuty → EventBridge → SQS → Fargate task (kronagent-serve) → Slack (outbound only)
                                  ├ triage: Claude on Amazon Bedrock, this account
                                  └ state: encrypted EFS, retained if the stack is deleted
```

- **No inbound ports.** The task's security group has no inbound rule. Approvals
  arrive over Slack Socket Mode ([`slack/README.md`](slack/README.md)), and the
  console is reached through ECS Exec, which is authenticated by IAM.
- **Read-only by default.** The task role carries the same observe policy as the
  cross-account observe role. `EnableContainment=true` attaches the contain
  policy (no terminate) and turns dry-run off. Even then, every action needs an
  approval in Slack or an allowlist promotion.
- **One task at a time,** because the state on EFS assumes a single writer.
- **Cost:** about $10–15 a month for Fargate (0.25 vCPU, 1 GB) and EFS, plus
  Bedrock tokens per finding. There's no NAT gateway or load balancer.

**Before you deploy:**

1. GuardDuty is enabled in the region. The stack doesn't enable it, because an
   account has one detector per region.
2. Model access to the chosen Claude model is enabled in the Bedrock console.
3. *(Optional)* A Slack app for approvals, from [`slack/README.md`](slack/README.md).

**Deploy:**

```bash
aws cloudformation deploy \
  --stack-name kronagent \
  --template-file deploy/cloudformation/kronagent-in-account.json \
  --capabilities CAPABILITY_IAM \
  --parameter-overrides SlackAppToken=xapp-... SlackBotToken=xoxb-... SlackChannelId=C0123456789 \
      SlackUserMapping='{"U0123ABC":"alice"}'
```

**Add the first operator.** The registry starts empty, and an empty registry
authorizes nobody, so no Slack click is honoured until you do this:

```bash
CLUSTER=$(aws cloudformation describe-stacks --stack-name kronagent \
  --query "Stacks[0].Outputs[?OutputKey=='ClusterName'].OutputValue" --output text)
TASK=$(aws ecs list-tasks --cluster "$CLUSTER" --query 'taskArns[0]' --output text)
aws ecs execute-command --cluster "$CLUSTER" --task "$TASK" --container kronagent \
  --interactive --command "kronagent-operators add alice --roles admin"
```

ECS Exec needs the AWS CLI's Session Manager plugin installed locally. The same
`execute-command` runs `kronagent-preflight`, `kronagent-approve list`
and `kronagent-halt status`.

**Check it end to end:** `aws guardduty create-sample-findings --detector-id <id>`
should produce triage in the logs, and an approval card in Slack, within a
minute or two.

**Turn on containment** after you've watched it in dry-run:
`--parameter-overrides EnableContainment=true QuarantineSecurityGroupId=sg-…
QuarantineNaclId=acl-…`. Turn it off the same way.

**Teardown:** `aws cloudformation delete-stack --stack-name kronagent`. The EFS
file system holding the audit log is retained on purpose. Delete it yourself
once you no longer need the record.

## 1. Prerequisites to provision once (by a human, out of band)

Kronagent references two pre-provisioned resources by id — it never creates them, so
it never needs `create-security-group` / `create-network-acl` privileges.

| Resource | Purpose | Wire into Kronagent via |
|---|---|---|
| **Quarantine security group** — a deny-all SG (no ingress, no egress) in each VPC you protect | `ISOLATE_INSTANCE_SG` swaps a compromised instance into this SG, cutting all traffic while preserving the instance for forensics | `KRONAGENT_QUARANTINE_SG_ID=sg-xxxx` |
| **Quarantine NACL** — a network ACL whose entries Kronagent manages | `BLOCK_IP` adds a deny entry for an attacker IP here; rollback removes it | `QUARANTINE_NACL_ID` in the policy ARN |

## 2. Substitute the placeholders in `kronagent-iam-policy.json`

> **These files are generated.** `deploy/cloudformation/*.json` and
> `deploy/kronagent-iam-policy.json` are rendered from the policy functions in
> `kronagent/connect.py` by `deploy/publish_templates.py`, and CI fails on drift.
> Change the grant there and run `python3 deploy/publish_templates.py --write`.
>
> They were three hand-maintained copies of one grant, and they had drifted five
> ways — including a NACL statement that granted every ACL in the account while
> the table below promised it granted exactly one. Substitute the placeholders in
> a *copy*; a hand edit committed here is a CI failure, by design.

| Placeholder | Replace with |
|---|---|
| `ACCOUNT_ID` | your 12-digit AWS account id |
| `REGION` | the operating region, e.g. `us-east-1` (must match `AWS_REGION` / `KRONAGENT_QUARANTINE_SG_ID`'s region) |
| `QUARANTINE_NACL_ID` | the real `acl-xxxx` id of the quarantine NACL |
| `QUARANTINE_SG_ID` | the real `sg-xxxx` id of the quarantine security group |
| `aws` (in `arn:aws:…`) | `aws-us-gov` in GovCloud, `aws-cn` in China regions — leave as-is in commercial regions |

```bash
sed \
  -e 's/ACCOUNT_ID/123456789012/g' \
  -e 's/REGION/us-east-1/g' \
  -e 's/QUARANTINE_NACL_ID/acl-0abc123/g' \
  -e 's/QUARANTINE_SG_ID/sg-0def456/g' \
  deploy/kronagent-iam-policy.json > my-kronagent-policy.json
```

## 3. Attach the policy to a dedicated Kronagent principal

Give Kronagent its **own** IAM role/user — never reuse an existing operator or CI
identity. Prefer a role assumed via short-lived credentials (STS) over a
long-lived access key.

```bash
aws iam create-policy \
  --policy-name KronagentContainmentLeastPrivilege \
  --policy-document file://deploy/kronagent-iam-policy.json

# then attach the returned ARN to the Kronagent role/user
```

## 4. Statement-by-statement rationale

| Sid | Action(s) | Kronagent action class | Scoping notes |
|---|---|---|---|
| `DisableAndReenableAccessKeys` | `iam:UpdateAccessKey` | `DISABLE_ACCESS_KEY` (+ reactivate rollback) | `iam:UpdateAccessKey` has **no** resource-level condition for the key id, so it is scoped to `user/*` in this account only. |
| `QuarantineDenyAllInlinePolicyOnly` | `iam:PutUserPolicy`, `iam:DeleteUserPolicy` | `ATTACH_DENY_ALL_TO_PRINCIPAL` (+ rollback) | `Condition` pins these to **exactly** the inline policy name `kronagent-quarantine-deny-all` — they cannot touch any other inline policy. |
| `RevokeRoleSessionsInlinePolicyOnly` | `iam:PutRolePolicy`, `iam:DeleteRolePolicy` | `REVOKE_ROLE_SESSIONS` (+ rollback) | Same single-policy-name pin (`kronagent-revoke-sessions`). Classified **destructive** in the policy engine → never auto-executes. |
| `ReadStateForRollbackCapture` | `ec2:DescribeInstances`, `ec2:DescribeNetworkAcls` | supports `ISOLATE_INSTANCE_SG`, `BLOCK_IP` | Read-only, and **required, not optional**: both run *before* their mutation, so without them containment does not degrade — it fails outright. EC2 `Describe*` does not support resource-level permissions (AWS limitation) → `Resource: *`. |
| `IsolateInstanceIntoQuarantineSG` | `ec2:ModifyInstanceAttribute` | `ISOLATE_INSTANCE_SG` | Scoped to instances in the region **and to the quarantine SG by ARN**. AWS evaluates this action against the security group named in `Groups=` as well as the instance, so both ARNs are needed — and naming the SG means this role can move an instance into quarantine and nowhere else. |
| `BlockIpAtQuarantineNacl` | `ec2:CreateNetworkAclEntry`, `ec2:DeleteNetworkAclEntry` | `BLOCK_IP` (+ rollback) | Pinned by **ARN** to the single quarantine NACL. Kronagent cannot modify any other NACL. |
| `TerminateInstancesInRegion` | `ec2:TerminateInstances` | `TERMINATE_INSTANCE` | Irreversible, destructive, always human-approved. **Consider deleting this statement** until you actually need the terminate class — least privilege means granting it only when used. |

## 5. Live ingestion: GuardDuty → EventBridge → SQS

Kronagent reads live findings by long-polling an SQS queue. Set `KRONAGENT_SQS_QUEUE_URL`
and `run_slice.py` switches from file replay to the live source automatically;
unset it to fall back to replaying `samples/`.

```
KRONAGENT_SQS_QUEUE_URL=https://sqs.us-east-1.amazonaws.com/123456789012/kronagent-findings
AWS_REGION=us-east-1
```

**Wiring (provision once):**

1. **SQS queue** `kronagent-findings` with:
   - **visibility timeout ≥ 60s** — must exceed the max per-finding processing
     time (LLM triage + containment). A message is invisible while Kronagent
     processes it and is deleted only after it's fully handled and audited
     (ack-after-process); too short a timeout causes double-processing.
   - a **redrive policy → dead-letter queue** `kronagent-findings-dlq` with
     `maxReceiveCount` ~5. Messages that don't parse as GuardDuty findings are
     **left in place, not deleted**, so SQS moves them to the DLQ instead of the
     pipeline losing them. Without a DLQ, a poison message redelivers forever.
2. **EventBridge rule** matching GuardDuty findings, targeting the queue:
   ```json
   { "source": ["aws.guardduty"], "detail-type": ["GuardDuty Finding"] }
   ```
   Add an SQS queue policy allowing `events.amazonaws.com` to `sqs:SendMessage`
   to the queue ARN. (A GuardDuty → EventBridge → **SNS** → SQS topology also
   works — the consumer unwraps the SNS `Notification` envelope automatically.)
3. **Attach `kronagent-sqs-ingestion-policy.json`** to the Kronagent principal — a
   read-only grant (`ReceiveMessage`/`DeleteMessage`/`GetQueueAttributes`) scoped
   to the one queue ARN. This is separate from the containment policy: ingestion
   is read-only and touches only the queue; containment is write and touches AWS
   infrastructure. Keeping them separate keeps each grant minimal.

**Delivery semantics:** at-least-once. On a crash mid-processing the message
reappears after the visibility timeout and is re-processed — a finding is never
silently lost. Re-processing is safe because containment actions are idempotent
and approval-gated.

## 6. Honest limitations

- **Three actions can't be fully resource-conditioned by AWS** (`iam:UpdateAccessKey`,
  `ec2:DescribeInstances`, and the target-SG on `ec2:ModifyInstanceAttribute`).
  Where the IAM grammar can't express the constraint, Kronagent enforces it in code
  and in the policy engine — defense in depth, but worth knowing the boundary.
- **This policy is the containment executor's grant only.** The Kronagent host also
  needs read access to its telemetry source (GuardDuty → EventBridge → SQS);
  that is a separate, read-only policy not included here.
- **Rotate to STS/short-lived credentials for production.** A static access key
  with this policy is still a high-value target; scope it with an SCP and a
  permissions boundary, and prefer role assumption.

## 7. Kubernetes Deployment with Helm

Production Kubernetes Helm chart templates are available in [`deploy/helm/kronagent/`](helm/kronagent/):

```bash
# Lint the chart
helm lint deploy/helm/kronagent

# Dry-run template rendering
helm template kronagent deploy/helm/kronagent --values deploy/helm/kronagent/values.yaml

# Install/upgrade in cluster
helm upgrade --install kronagent deploy/helm/kronagent \
  --namespace kronagent --create-namespace \
  --set config.dryRun=true
```
